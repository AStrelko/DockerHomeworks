Проєктування середовища для розробки платформи онлайн-бронювання готелів

1. Аналіз архітектури

Кожен бізнес-компонент може працювати як окремий мікросервіс. Це варіант проєктування, а не обов’язкова вимога Docker: для невеликого проєкту частину функцій можна спочатку об’єднати.

Компонент
Відповідальність

Сервіс авторизації              
Реєстрація та вхід користувачів, перевірка облікових даних, видача токенів, керування правами доступу.

Каталог готелів                 
Дані про готелі, номери, зручності, фотографії та пошук доступних пропозицій.

Сервіс бронювання               
Створення, перегляд і скасування бронювань; перевірка доступності номера на потрібні дати; захист від  подвійного бронювання.

Сервіс оплати
Створення платежу, обробка результату через платіжного провайдера, фіксація статусу платежу та повернення коштів. Дані банківської картки доцільно обробляти через провайдера.

Сервіс сповіщень
Надсилання підтверджень бронювання, повідомлень про оплату та нагадувань електронною поштою або іншими каналами.

База даних
Зберігання даних. Сама база даних є інфраструктурним компонентом, а не мікросервісом. У навчальній схемі показано один сервер БД; у зрілішій системі кожен сервіс може володіти власними даними, щоб інші сервіси не змінювали його таблиці напряму.

2. Аналіз контейнеризації

Окремий контейнер для кожного сервісу дає змогу задавати його залежності, конфігурацію та версію незалежно від інших. Наприклад, оновлення сервісу сповіщень не потребує перевстановлення каталогу. Контейнери можна запускати, зупиняти й масштабувати окремо; збій одного процесу менше впливає на інші процеси. Ізоляція не замінює налаштування доступу, мережі та безпеки.

Базу даних теж можна запускати в окремому контейнері для розробки, але її дані потрібно зберігати в Docker volume, щоб вони не зникли після видалення контейнера. У виробничому середовищі команда може обрати керовану базу даних замість контейнера.

3. Робота без контейнеризації

Якщо встановити всі компоненти безпосередньо на одному комп’ютері, можуть виникнути конфлікти версій мов, бібліотек і бази даних; різні сервіси можуть претендувати на один порт. Розробнику доведеться вручну повторювати налаштування на кожному комп’ютері. Один сервіс може змінити спільне оточення та зламати інший. Складніше прибрати застосунок без залишків, відтворити помилку колеги та запустити кілька версій системи паралельно. Якщо цей єдиний комп’ютер недоступний, недоступними можуть стати всі компоненти.

Контейнери спрощують відтворення середовища, але самі по собі не забезпечують відмовостійкість одного комп’ютера.

4. Компоненти Docker

Поняття
Роль у проєкті

Docker Daemon
Фонова служба Docker Engine, яка збирає образи та створює, запускає й зупиняє контейнери за командами клієнта.

Docker CLI
Командний інтерфейс docker, через який розробник надсилає команди демону: наприклад, docker build, docker run, docker ps.

Dockerfile
Текстовий рецепт складання образу конкретного сервісу: базовий образ, копіювання файлів, встановлення залежностей, команда запуску.

Docker Image
Незмінний шаблон із застосунком і його потрібними файлами, з якого створюють контейнери. Для сервісів можна збирати окремі образи.

Docker Container
Запущений екземпляр образу з власним процесом та ізольованим середовищем. Наприклад, контейнер каталогу обробляє запити до каталогу.

Docker Registry
Сховище образів, наприклад Docker Hub або приватний реєстр команди. Розробники та сервери отримують із нього потрібні версії образів.

Типовий шлях: описати збірку в Dockerfile → зібрати Image → за потреби завантажити його в Registry → запустити Container. Команду через Docker CLI приймає Docker Daemon.

5. Віртуалізація та контейнеризація

Окрема віртуальна машина містить власну гостьову операційну систему. Контейнери використовують ядро операційної системи хоста і зазвичай потребують менше ресурсів та швидше запускаються. Тому на машині розробника зручніше підняти кілька сервісів у контейнерах, ніж окрему ОС для кожного сервісу. Образи також допомагають команді відтворювати однакове середовище.

Віртуальні машини дають інший рівень ізоляції та дозволяють запускати різні гостьові ОС. На Windows Docker Desktop зазвичай використовує WSL 2 для Linux-контейнерів: контейнери не працюють безпосередньо на ядрі Windows.

Схема архітектури

flowchart TB
    U["Користувач"] --> API["Вхідний API / маршрутизація"]
    API --> AUTH["Авторизація"]
    API --> CAT["Каталог готелів"]
    API --> BOOK["Бронювання"]
    BOOK --> PAY["Оплата"]
    BOOK --> NOTIF["Сповіщення"]
    PAY --> NOTIF
    AUTH --> DB[("База даних")]
    CAT --> DB
    BOOK --> DB
    PAY --> DB
    NOTIF --> DB
    PAY --> PROVIDER["Зовнішній платіжний провайдер"]
    NOTIF --> CHANNEL["Email / інші канали"]

На схемі стрілки до БД позначають зберігання даних, а не дозвіл кожному сервісу змінювати таблиці інших сервісів. Вхідний API є точкою маршрутизації запитів до потрібних сервісів. Кожен сервіс можна розмістити в окремому контейнері; БД — в окремому контейнері з volume для навчального середовища.

Висновок:
 Docker допоможе команді однаково запускати компоненти платформи на робочих комп’ютерах, незалежно збирати й оновлювати сервіси та спростити їх подальше розгортання.
