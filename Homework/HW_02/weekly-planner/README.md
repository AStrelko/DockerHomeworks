# Мій тижневик — менеджер подій у Docker

У цій домашній роботі я розробив React-застосунок для планування подій у календарі та підготував Docker-образ для його запуску. Із запропонованих тем я обрав **менеджер подій**. Інтерфейс застосунку українською мовою.

## Можливості застосунку

У календарі я можу вибрати день і додати подію із назвою, датою та часом. Підтримуються два типи записів:

- **Запланована подія** належить конкретній даті: наприклад, зустріч 20 листопада о 15:00.
- **Щорічна подія** повторюється в той самий день і місяць кожного року: наприклад, день народження або річниця.

Події вибраного дня показуються праворуч від календаря у порядку часу. Кожну подію можна відзначити виконаною, зняти відмітку або видалити. Для щорічної події виконання зберігається окремо за кожний рік: відмітка у 2026 році не робить її автоматично виконаною у 2027 році.

Щоб одразу бачити характер подій, я використав три кольори календаря:

| Колір дня | Що означає |
| --- | --- |
| Рожевий | Є щорічна подія. |
| Синій | Є запланована подія. |
| Світло-фіолетовий | Є події обох типів. |

Дані зберігаються у `localStorage` браузера після кожної зміни. Завдяки цьому вони залишаються після оновлення сторінки та перезапуску контейнера в тому самому браузері. Серверної бази даних у цьому навчальному проєкті немає. Події не синхронізуються між пристроями, а системні сповіщення не надсилаються. Щорічна подія, записана на 29 лютого, відображається тільки у високосні роки.

## Як побудований проєкт

| Файл | Моя реалізація |
| --- | --- |
| `src/App.tsx` | Головний компонент: стан застосунку, календар, форма додавання, список подій, відмітка виконання та видалення. |
| `src/calendar.ts` | Допоміжні функції для дат: ключ `YYYY-MM-DD`, сітка місяця з понеділка, перехід між місяцями й форматування дати. |
| `src/events.ts` | Типи подій, читання й перевірка даних із `localStorage`, збереження, пошук щорічних повторень та стан виконання. |
| `src/main.tsx` | Початкова точка React: відображення `App` в елементі `root`. |
| `src/style.css` | Стилі сторінки, кольорові стани календаря та адаптація до вузьких екранів. |
| `index.html` | HTML-сторінка з елементом для React. |
| `package.json`, `package-lock.json` | Залежності та команди для запуску і збірки застосунку. |
| `Dockerfile` | Рецепт власного Docker-образу. |
| `.dockerignore` | Виключає локальні `node_modules`, `dist` та службові файли з контексту Docker-збірки. |
| `REPORT.md` | Окремий короткий звіт із відповідями на теоретичні запитання домашньої роботи. |

## Як я підготував Docker-образ

За основу власного образу я взяв `node:22-alpine`. У `Dockerfile` задав робочу директорію `/app`, скопіював `package.json` і `package-lock.json`, установив залежності через `npm ci`, а потім скопіював решту файлів проєкту. Контейнер запускає сервер Vite командою `npm run dev`.

В `package.json` Vite налаштований слухати `0.0.0.0`, щоб до нього можна було звернутися поза контейнером. Директива `EXPOSE 5173` описує внутрішній порт, а під час запуску я опублікував його на комп'ютері через `-p 5173:5173`. У браузері застосунок доступний за адресою `http://localhost:5173`.

| Команда, яку я використав | Результат |
| --- | --- |
| `docker build -t weekly-planner:1.0 .` | Зібрав власний образ із тегом `1.0` на основі `Dockerfile`. |
| `docker run -d --name weekly-planner -p 5173:5173 weekly-planner:1.0` | Створив і запустив контейнер `weekly-planner` у фоні з доступом через браузер. |
| `docker ps` | Перевірив, що контейнер працює і порт опублікований. |
| `docker logs weekly-planner` | Переглянув повідомлення Vite після запуску. |
| `docker inspect --format '{{.State.Status}}' weekly-planner` | Перевірив стан `running`. |
| `docker stop weekly-planner` та `docker start weekly-planner` | Перевірив зупинку і повторний запуск того самого контейнера. |

У скриншотах до роботи показані успішна збірка образу, запущений контейнер, логи, його зупинка й повторний запуск, а також сторінка застосунку в браузері.

## Теги образів 1.0 і 2.0

Для виконання завдання з версіонування я додав образу другий тег командою `docker tag weekly-planner:1.0 weekly-planner:2.0`. Через `docker image ls weekly-planner` перевірив наявність обох тегів. Команда `docker image inspect` показала однаковий ID: **це два теги одного й того самого образу**, а не дві різні збірки застосунку.

Якщо я зміню код і хочу отримати справжню нову версію образу, потрібно знову виконати збірку з тегом `2.0`. Теги зручні для позначення релізів, перевірки потрібної версії та повернення до попередньої збірки.

## Що я перевірив

- Збірка React і перевірка TypeScript командою `npm run build` завершилися успішно.
- Docker зібрав образ `weekly-planner:1.0` із файлу `Dockerfile`.
- Контейнер `weekly-planner` відображався у `docker ps`, а в логах було видно запуск Vite.
- Застосунок відкривався за адресою `http://localhost:5173`.
- Після `docker stop` контейнер переходив у зупинений стан, а після `docker start` знову працював.
- Обидва теги, `1.0` і `2.0`, були доступні локально та мали однаковий ID образу.

Скриншоти практичної перевірки додаються до здачі роботи окремо. Теоретичні відповіді також винесено у `REPORT.md`.
